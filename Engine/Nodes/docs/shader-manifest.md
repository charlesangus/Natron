# Network node manifests

A manifest lists the nodes one network target offers, with every attribute, its type and default,
and every output. Natron builds its network nodes from manifests (see `shader-nodes.md`), so it
needs no renderer at build or test time: the manifests are generated from the renderers in the dev
image and committed. Shader manifests are the first content. Kernel and channel networks will add
manifests in the same format.

| File | Generated by | Source |
| --- | --- | --- |
| `Engine/Nodes/Scene/Shaders/manifest/cycles.json` | `tools/shaders/dump_cycles_manifest.cpp` | Cycles' `NodeType` registry, read from the bundled `hdCycles.so` |
| `Engine/Nodes/Scene/Shaders/manifest/moonray.json` | `tools/shaders/generate_moonray_manifest.py` | MoonRay's rdl2 class JSON (`<moonray>/coredata/`, or exported from `rdl2dso/` with `--from-dsos`) |

Hand-written layout tables sit next to them (`cycles_layout.json`, `moonray_layout.json`; see
[Layout tables](#layout-tables)), and `tools/shaders/check_manifest.py` checks them against the
manifests.

## Regenerating

Both generators run inside the dev image, which carries the bundled renderers:

```
python3 tools/shaders/generate_moonray_manifest.py
cmake -S tools/shaders -B build/shader-tools -DCYCLES_SOURCE_DIR=/usr/local/share/cycles-src
cmake --build build/shader-tools
build/shader-tools/dump_cycles_manifest --library /usr/local/plugin/usd/hdCycles.so \
    --source /usr/local/plugin/usd/hdCycles/SOURCE \
    --output Engine/Nodes/Scene/Shaders/manifest/cycles.json
```

The image builds Cycles only into `hdCycles.so`, with its symbols hidden. The dump tool loads the
plug-in, finds `ccl::NodeType::type_names` and `ccl::NodeType::find` in the library's ELF symbol
table, and reads the registry through the headers of the same Cycles commit. Output is
deterministic: regenerating from the same renderers gives the same bytes.
The image keeps the headers of hdCycles' Cycles commit in `/usr/local/share/cycles-src`
(`tools/ci/local/build-cycles.sh`), which is all the dump tool compiles against.

`tools/shaders/check_manifest_drift.sh` regenerates both manifests in the image and compares them
with the committed files, naming every node, attribute and output that changed, so a renderer
upgrade cannot change shaders unnoticed. `.github/workflows/dev-image.yml` runs it in every newly
built image before pushing it, with the checkout mounted; by hand, in the image:

```
tools/shaders/check_manifest_drift.sh
```

## Format

The file is one JSON object. Lists of scalars are written on one line; everything else follows
Python's `json.dumps(indent=2)`.

| Key | Meaning |
| --- | --- |
| `schema` | Format version, `1`. |
| `renderer` | `cycles` or `moonray`. |
| `source` | Where the data came from: repository, commit (and MoonRay's shader submodules), generator. |
| `nodes` | The nodes, sorted by `id`. |

### Node

| Key | Meaning |
| --- | --- |
| `id` | The node's identifier, written to USD as `info:id`. Cycles: `cycles_<type>`, the form hdCycles resolves (`src/hydra/material.cpp`). MoonRay: the rdl2 class name. |
| `name` | The renderer's own name for the node: the Cycles node type or the rdl2 class. |
| `kind` | Cycles: `shader` (has a closure output), `texture`, `displacement` or `utility`. MoonRay: `material`, `map`, `normal_map`, `displacement` or `volume`. |
| `targets` | The network targets the node supports: `cycles` or `moonray` here. Kernel nodes will declare `kernel`, channel nodes `channels`. |
| `groups` | Optional. The order of the attribute groups (MoonRay's `grouping` metadata). Cycles groups come from `cycles_layout.json`. |
| `attributes` | The inputs, in the renderer's declaration order. |
| `outputs` | The outputs, in the renderer's order. |

Later node families add optional keys (a kernel node's code template, a channel node's cook entry);
nothing above is specific to shaders.

### Attribute

| Key | Meaning |
| --- | --- |
| `name` | The renderer's attribute name. The knob's script name is this name sanitised, and its label the readable form of that (`base_color` → "Base Color"). |
| `type` | The renderer's type name. Cycles: `SocketType::type_name` (`float`, `color`, `enum`, `closure`, `array_float`, ...). MoonRay: the rdl2 `attrType` (`Float`, `Rgb`, `SceneObject*`, `FloatVector`, ...). |
| `default` | The renderer's default. Absent for attributes with no value (`port_only`). Vectors and colours are lists, matrices are lists of rows (MoonRay) or the 12 floats of a 3×4 transform (Cycles). An enum default is the value as it is authored: the enum name for Cycles, the integer for MoonRay. |
| `enum` | Optional. The choices, `{name, value}`, sorted by value. |
| `linkable` | The attribute can be driven by a connection, so it can be promoted to a port. |
| `port_only` | The attribute has no value and is always a port: Cycles closures, MoonRay `SceneObject` bindings. Implies `linkable`. |
| `array` | The attribute holds a list (ramps, curves, tile lists). |
| `group` | Optional. MoonRay's group for the attribute. Absent means the node's main page. |
| `comment` | Optional. MoonRay's description, used as the tooltip. |

Optional renderer metadata, kept so later milestones need not regenerate:

| Key | Renderer | Meaning |
| --- | --- | --- |
| `ui_name` | Cycles | The socket's UI name. hdCycles matches connections on either `name` or `ui_name`. |
| `default_link` | Cycles | What an unconnected socket reads instead of its value: `texture_generated`, `texture_uv`, `normal`, `position`, `tangent`, ... |
| `subgroup` | MoonRay | A sub-heading within the group. |
| `interface` | MoonRay | The rdl2 interface a binding accepts (`Map`, `NormalMap`, `Material`, ...). |
| `asset` | MoonRay | The value is a file path. |
| `min`, `max` | MoonRay | Suggested range. |
| `aliases` | MoonRay | Other names the attribute answers to. |
| `enable_if`, `disable_when` | MoonRay | MoonRay's UI conditions: a `{attribute: value}` object, or the raw text when it is not one. |
| `structure` | MoonRay | `{type, name, path}` for attributes that together form a ramp (`ramp_color`, `ramp_float`). |

### Output

| Key | Meaning |
| --- | --- |
| `name` | The output's name. Every MoonRay shader has one output, `out`: rdl2 binds whole objects. |
| `type` | The renderer's type name, as for attributes. MoonRay outputs are `SceneObject*`. |
| `interface` | MoonRay only: the rdl2 base type the object binds as (`Map`, `NormalMap`, `Material`, `DwaBaseLayerable`, ...). |
| `array` | The output is a list. |
| `ui_name` | Cycles only, as for attributes. |

## What is left out

- Cycles: OSL script nodes (decision `2026-11-05-no-cycles-osl`), and the registry's internal
  node types: `output`, the `convert_*` conversions, `proxy`, `set_normal` and
  `mix_closure_weight`. Internal sockets (`SocketType::INTERNAL`, such as Principled BSDF's
  `surface_mix_weight`) are not attributes.
- MoonRay: display filters, and every class that is not a material, map, normal map, displacement
  or volume shader (lights, light filters, cameras, geometry, sets, render outputs). The `Test*`
  classes MoonRay builds for its own unit tests (`TestInputsMap`, `TestColorOutputMap`, ...) are
  not user shaders and are left out too.

## Layout tables

`cycles_layout.json` and `moonray_layout.json` hold what the renderers do not say:

```
{
  "schema": 1,
  "renderer": "cycles",
  "nodes": {
    "cycles_principled_bsdf": {
      "groups": [{"name": "Base", "attributes": ["base_color", "metallic", "..."]}, "..."],
      "key_ports": ["base_color", "metallic", "..."]
    }
  }
}
```

- `groups` (Cycles only, required for every Cycles node): the knob pages, in order, each listing its
  attributes. MoonRay groups come from the manifest.
- `key_ports` (both renderers): for a node with more than 12 ports (linkable attributes), the
  attributes shown as ports by default, at most 12. Port-only attributes are always ports and are
  not listed. A node with 12 ports or fewer shows every linkable attribute and has no list.

`check_manifest.py` fails when a table names a node or attribute the manifest does not have, puts
an attribute in two groups, misses a node, or lists key ports that are not linkable, and it reports
every Cycles attribute that no group names: those land in an "Other" group.

## Node docs and the coverage audit

`tools/shaders/audit_shader_nodes.py --docs` writes one page per shader under
`Engine/Nodes/Scene/docs/shaders/<renderer>/<id>.md`: its outputs, and per page every attribute
with its label, script name, type, default and whether it is a knob, a port or both.
`--check-docs` (ctest `ShaderDocsPython`) fails when a committed page differs from the manifests;
regenerate the pages whenever a manifest or layout table changes.

The same script audits the nodes Natron builds: `Tests/Scene/ShaderAudit_Test.cpp` runs its
`audit()` in the test application, which creates every shader of both renderers by ID and checks
each manifest attribute's knob (type, dimensions, label, default, options) or port, which
attributes can be promoted, and the ports a new node starts with. It must report no problem.
