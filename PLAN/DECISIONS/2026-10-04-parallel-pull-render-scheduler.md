# M63: make the pull concurrent instead of building an up-front task graph

2026-10-04 (planning consultant, scouting `milestone/m63-task-graph-render-scheduler` at `20aa6f102`; pending the user's confirmation).

M63 keeps the recursive `renderRoI` pull and adds concurrency where the pull already fans out. Today `treeRecurseFunctor` pre-renders a node's inputs one after another (`Engine/ParallelRenderArgs.cpp:133-305`, `inputEffect->renderRoI` at `:282`). Under M63 every input after the first becomes a task on the global `QThreadPool` and the calling thread renders the first input itself. The join is claim-or-wait: a child that has not started is claimed and run inline; only children already running are waited on. No thread ever waits on queued work, so nested fork-join cannot deadlock however small the pool. Each node gets exactly today's call, RoI, time and args; only the order changes.

Two layers, in order. First, shared-pool discipline, because most of the measured "3 of 4 cores" is not a scheduling problem: in NatronRenderer `startWritersRendering` runs each blocking render inside `QtConcurrent::blockingMap` (`Engine/AppInstance.cpp:1814`), which can park the render on a pool thread that then sleeps for the whole render (`Engine/BlockingBackgroundRender.cpp:66-70`), losing one of four slots and making `getNCPUsAvailableForEffect` (`Engine/AppManager.cpp:2923-2950`) tell plugins there are three CPUs; viewer current-frame renders are also pool runnables (`Engine/OutputSchedulerThread.cpp:4072-4077`) that hold their slot while the multithread suite sleeps in `future.waitForFinished()` (`Engine/OfxHost.cpp:1361-1362`). The fix: the suite and host frame threading switch to caller-participating `blockingMapped`, and any pool thread that must block gives up its slot while waiting. Second, parallel branches inside the pull, behind a setting that ships off and is turned on after the pixel, abort and GUI gates pass.

Why not the stub's up-front graph executor: the request pass already merges every consumer's RoI per (node, time, view) (`ParallelRenderArgs.cpp:423-431`) and renders read that merged RoI (`:257`), so the first render of a fan-out node covers all its consumers and the second either hits the cache (nodes with more than one output always cache, `Engine/Node.cpp:7212`) or waits on the trimap (`EffectInstancePrivate.cpp:626`), exactly as parallel frame renders do today. A bottom-up executor would have to re-derive outside `renderRoI` everything it decides (identity redirection, transform reroutes, mask and rotopaint skips, rect splitting, the 4-frame prefetch cap, whether to cache), keep a frame-local store for uncached images, and fall back to pulling whenever a plugin's `getImage` disagrees with the prediction. It adds critical-path ordering, which nothing measured needs.

Rejected: a dedicated pool for node tasks (the suite, host frame threading, deep chunks and row bands all size themselves from the global pool, so a second pool means 8 threads on 4 cores); doing M31.P1.T1 (`RenderEngine` on `Node`) first (nothing here owns a graph, and render roots and entry points do not change); relying on frame overlap (writers already render frames in parallel, `OutputSchedulerThread.cpp:1507-1550`, and September's 8-frame range renders were only 1.1–1.2x better per frame; M63 measures this and tunes it only if occupancy stays low).

Constraints: branch tasks enter `AppTLS::SpawnedThreadScope` with the frame's root render thread as spawner, under a new spawn kind that copies only `frameArgs`, so spawner chains stay at depth ≤2 (`getSpawnerChain` stops at 16 and a comp DAG nests deeper). Forks happen only before a render action, never inside one (plugin instance locks are held there, `EffectInstanceRenderRoI.cpp:1424-1471`), only for CPU image inputs with an RoI of at least 256×256; deep, geometry and OpenGL inputs stay inline.

Honest gains on the 4-core N100: chains run 3 threads 83.5% of the time, so filling the fourth core caps the gain at about 1.26x (target ≥1.15x for HD chain/mixed). Wide/comp HD 100 run at parallelism ~2.55, so perfect occupancy at constant work caps at ~1.57x (target ≥1.3x per frame, stretch 1.45x, mean running threads ≥3.4). The stub's 1.8x per frame is not reachable on 4 cores and is dropped.

Risks: TLS races while the spawner keeps rendering (copy only `frameArgs`); deadlock in nested waits (claim-or-wait plus releasing the slot while blocked); higher peak RSS from intermediates in flight (depth-first priority; RSS measured); host-frame-threaded CImg plugins already tile differently with pool load (`EffectInstanceRenderRoI.cpp:1154-1165`), so their output is compared within a tolerance; Python GIL contention with many expressions; plugins that overstate their thread safety. The setting defaulting off until the gates pass contains all of these.

Moved to M31: a per-render context object replacing per-effect TLS frame args, and `FrameView_compare_less` (`ParallelRenderArgs.h:221` returns true for `lhs.view > rhs.view`, not a strict weak ordering). M64 becomes tiling inside the pull.
