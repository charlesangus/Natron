# M63: a task-graph scheduler built from the request pass, executed on the one global pool, with `renderRoI` as the task body

2026-10-04 (planning consultant, fable, scouting `milestone/m63-task-graph-render-scheduler` at `20aa6f102`). Draft; finalised with the After-M63 numbers at M63.P6.T1.

**Architecture.** Each frame render builds a `FrameGraph` whose tasks are the (node, time, view, mipmap) tuples the existing request pass already enumerates (`EffectInstance::computeRequestPass` → `getInputsRoIsFunctor` → `treeRecurseFunctor(false)`, `Engine/ParallelRenderArgs.cpp:540/311/47`), with edges recorded during that same walk after mask filtering, transform rerouting, identity resolution and the 4-frame prefetch cap, i.e. exactly the set of `renderRoI` calls the pull's `treeRecurseFunctor(true)` would make. A task's body is today's `EffectInstance::renderRoI` on the merged `finalRoi`; its inputs are pre-rendered by predecessor tasks and handed over through a frame-local `FrameStore` that the pre-render (`ParallelRenderArgs.cpp:263-282`) and `getImage` consult before falling back to a nested pull. Cache policy, `shouldCacheOutput`, `visitsCount`, trimap and render-safety locks are untouched because they live inside `renderRoI`. An app-wide `RenderScheduler` (owned by `AppManager`) runs tasks as `QRunnable`s on `QThreadPool::globalInstance()`, the same pool the OFX multithread suite and host frame threading already use (`OfxHost.cpp:1361`, `EffectInstanceRenderRoI.cpp:1857`), with a priority queue ordered by (interactive-before-background, frame sequence, DFS post-order) so one frame's branches are drained depth-first, consecutive frames overlap only to fill idle threads, and in-flight intermediates stay bounded by about P partial branches; a byte budget gates the start of new branches. Node tasks never block on other tasks (dependency counting); the only blocking is the plugin's fork-join, which is deadlock-free on Qt 6 because a waiter steals its own queued runnable (to be confirmed in the Qt 6.8 source at P3.T3). Frame TLS reaches a task in O(1) by installing a per-frame context pointer and materialising a node's `EffectTLSData` lazily from it, a direct extension of M62's per-holder lazy inheritance. Pool sizing keeps today's `noRenderThreads` semantics (0 → min(cores, RAM/3.5 GB)), so a 64-thread, 256 GB workstation gets a 64-wide pool and a 4-core, 15 GB box gets 4; `multiThreadNumCPUS` stays `poolMax − active + 1`, which hands a lone chain node the whole pool and a hundred ready branch tasks one thread each without new tuning.

**Why this and not the alternatives.** A concurrent pull (spawn the recursion) has no global view: no ordering, no memory bound on broad DAGs, unbounded nesting on deep chains, and it oversubscribes exactly as today's frame threads do. A bottom-up executor that bypasses `renderRoI` would re-implement caching, identity, transforms, masks, NaN handling and the trimap and could not be bit-exact in one milestone. Frame-only parallelism (what writers already do with `RenderThreadTask` QThreads, `OutputSchedulerThread.cpp:1508-1546`) does nothing for a single viewer frame or a wide comp, and its `adjustNumberOfThreads` heuristic throttles itself on pool activity. Tile/scanline streaming is M64's orthogonal gain and sits naturally on top of tasks.

**Expected gains, in scaling terms.** Available parallelism of a frame is its task count over its critical path; the scheduler should reach occupancy ≥0.8·P wherever that exceeds P. wide 100 has ~300 tasks over a ~9-deep critical path, so it saturates 4 or 32 threads; comp 100 similar. For chains, single-frame parallelism is the plugin kernel alone and Amdahl caps it (~20% serial engine/writer/plugin-setup work → 2.5 of 4 cores today, matching the measured 2.6, and only ~4.7 of 64); the scheduler's gain for chains is frame overlap, which pipelines the serial parts of frame f with kernels of f+1 up to K frames in flight. First data points on the 4-core host: comp/wide HD single frame from 2.55–2.58 busy cores to ≥3.2 and frame time ≤0.8× (6.65 s → ≤5.3 s, 3.23 s → ≤2.6 s); chains no slower (≤1.1×); range renders of chain 30 HD ≤0.85× per frame against a range baseline this milestone first records. On wide machines the same targets read as occupancy ≥0.8·P and speedup ≥0.8·P/parallelism_before.

**Risks.** TLS correctness on pool threads (racy; tests repeat 3× across pool sizes). Unpredicted `getImage` fetches fall back to nested pulls that may duplicate uncached work (counted in `RenderStats`; the equivalence suite asserts zero on known topologies). Memory on hundreds of branches (DFS priority plus the byte budget; measured in the pool-size sweep). Qt's steal-on-wait must be verified in the 6.8 source and stress-tested at pool size 1–2. OpenGL, active roto strokes, analysis renders and deep-output writers stay on the legacy path in v1. The viewer lands last, behind the writers, behind a setting that renders both ways.
