# Loops and I-nodes: architecture

Decided 2026-10-25 with the user (/cat-plan grill). Shake/PxF-style I-nodes, where a Map input drives the size or amount of an effect per pixel instead of blending, come two ways: **exact native I-variants** (IBlur, IErode, IDilate, ITransform, ICornerPin, IDefocus, ISharpen, IGlow, IBloom, IMedian, IDirBlur), registered separately from and sharing a class with each base node, and a **universal I-mode**: a Houdini-style LoopBegin/LoopEnd block around any subgraph whose Map-blend mode blends per pixel between iterations rendered at driven knob values. A single **Make I-Node** action swaps in an exact variant when one exists and wraps the selection in a loop otherwise. Loops also offer Accumulate, Feedback, frame iteration, single pass and a stop condition.

The loop driver is the per-context render core shared with Reverse-Flow Variables (E13), split out of M71 as M178 - Render Context Core: each iteration is a render context, and only nodes whose upstream read-set names a loop variable re-render per iteration. Rejected: hidden clone nodes (`ImageKey` includes the `Node*`, so no cache sharing; graph edits mid-render; O(N²) graph hotspots), knob-override render args (the same core without read-sets), and task-graph instancing as a separate design (it is how the core runs on the task graph). Managed knob drivers are native C++ because Python expressions take the GIL on render threads and the tree has no exprtk. Accumulate unrolls into a fold chain to bound memory; Map-blend culling uses graph continuation (M179) from the start.
