# Geometry bridges follow Solaris: file format layer in, packed prims and overrides out

2026-10-27. The user studied how Houdini moves SOP geometry into and out of USD and adopted three parts of it for M54 - SOPs-Style Geometry. This amends the bridge and display parts of `2026-09-18-geometry-is-a-fourth-data-kind.md`. The data kind itself is unchanged.

1. **`GeoToUSD` is a file format layer, not a copy.** Solaris's SOP Import writes a layer whose metadata points Houdini's Sdf file format plugin at a SOP node, and the plugin converts lazily. Copying into an anonymous layer is a separate, slower opt-in. Natron does the same: an `SdfFileFormat` plus an `SdfAbstractData` backed by the node's `GeoDetail` (format `natrongeo`) is the layer the node contributes to its `ScenePayload` stack. The Viewer and `USDRender` read the same layer. The layer is identified by node, output, view and mode, never by content hash. A hash change reloads it in place, so value-only changes reach Hydra as dirty points rather than a resync (the user chose this over a node-plus-hash identifier on 2026-10-27).
2. **Component display only in the geometry context.** LOPs select and edit whole prims, and component work stays in SOPs. In Natron, point and component picking and display exist only when the Viewer shows a geometry-kind node, highlighted with Storm's `HdSelection` plus guide prims. In the scene context, picking stays at prim level.
3. **`USDToGeo` → Geo → `GeoToUSD` works like SOP Modify.** Prims arrive as packed prims (transform, parent transform, bounds, source path; no topology), so they can be transformed without unpacking. Unpacking to full geometry happens only on request. When `GeoToUSD` has a Scene input, it writes the result back as `over` specs on the source paths.
