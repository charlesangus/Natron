# Native geometry follows SOPs

2026-11-08. While grilling M54 - SOPs-Style Geometry, the user set the rule for every native-geometry design question: "prefer doing things the same way SOPs does." Native geometry (`eDataKindGeometry`, `GeoDetail`, the `Geo*` nodes) is Natron's SOP context, not a LOP one. Its data model is Houdini's unified detail: one point pool, vertices and primitives indexing it, detail/primitive/vertex/point attribute classes, point/primitive/vertex/edge groups, paged copy-on-write storage with tombstoned deletes, and dense element numbers. It uses SOP attribute names (`P`, `N`, `uv`, `Cd`, `pscale`, `orient`, `path`, `name`) and contains no pxr types. `path` is an ordinary attribute, not a USD-style identity: only the bridges read it, partitioning the detail into USD prims as Solaris SOP Import does. Node behaviour follows the corresponding SOP (Edit, Transform, Merge, Blast, Scatter, Copy to Points, Attribute Wrangle, Python) unless a milestone records a reason to differ. This refines `2026-09-18-geometry-is-a-fourth-data-kind.md`, whose UsdGeom-shaped container sketch it replaces. The bridge model in `2026-10-27-geometry-bridges-follow-solaris.md` stands, except that serving the detail now partitions and re-indexes rather than handing out arrays unchanged.
