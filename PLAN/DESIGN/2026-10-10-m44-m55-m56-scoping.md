### M44 questions for you
1. **Modifier mapping** (Alt-drag is risky because many Linux window managers use it to move windows):
   - (a) Ctrl = hue, Shift = saturation, Ctrl+Shift = value, Meta = temperature.
   - (b) **Recommended:** two modifiers with two axes each. Ctrl+drag: horizontal = hue, vertical = saturation. Shift+drag: horizontal = temperature, vertical = value.
   - (c) Copy Nuke's swatch conventions exactly. You'd need to confirm them; I haven't verified Nuke's current bindings.
2. **Which controls get it:**
   - (a) **Recommended:** the `KnobGuiColor` swatch only.
   - (b) Also the `ColorSelectorWidget` popup.
   - (c) Also the node-colour button. This adds a real `M24` dependency, because M24.P3.T4 rewrites that path.
   - The viewer gain/gamma controls aren't colour knobs, so I'd leave them out.
3. **Working space and temperature model:**
   - (a) **Recommended:** HSV on the raw linear values, with temperature as a luminance-preserving R-up/B-down offset.
   - (b) Do the maths in display space through the viewer's OCIO/LUT. This touches M50 territory, so not now.

**What splice-into-pipe already does:** most of it exists.
- While dragging a node, `NodeGraph::checkForHints` highlights a nearby edge with `Edge::setUseHighlight`, shows the `_hintInputEdge` / `_hintOutputEdge` ghost edges, and pushes `InsertNodeCommand` on release (`Gui/NodeGraph15.cpp:237-255`).
- **What's missing:**
  - It only works while **Ctrl is held** (`doConnectionHints = controlDown`, `NodeGraph20.cpp:63`). Ctrl+Shift does merge hints instead.
  - It only works with **exactly one selected node** (`NodeGraph20.cpp:369`), so dragging groups or multiple nodes doesn't splice.
  - It turns itself off when the dragged node is already fully connected.
  - Backdrops are ignored.
  - There is no explicit marker showing where the node will be inserted.

**Plausible causes of a connected input with no pipe** (the stub says it needs a repro):
- (a) `NodeGui::refreshEdges` (`Gui/NodeGui.cpp:1313`) and `connectEdge` (`Gui/NodeGui.cpp:1876`) silently return when `_inputEdges.size() != getGuiInputs().size()`. This happens when a node's input count changes at runtime (Merge-style dynamic inputs, a group gaining an Input node, a typed-input change) before the `inputsInitialized` signal rebuilds the edges.
- (b) `refreshEdges` skips (`continue`) any input whose NodeGui doesn't exist yet, for example because of node creation order during project load or paste. Nothing retries it afterwards.
- (c) `initializeInputs` creates the edges hidden and inactive when the NodeGui is `!isVisible()` (`Gui/NodeGui.cpp:1571`). Later visibility is only changed through `refreshEdgesVisility`.
- (d) Overlapping source and destination nodes mean `initLine` finds no source intersection, so only a stub (or nothing) gets drawn.
- (e) `getHideInputsKnobValue()` and `isInputVisible()`. These are intended behaviour, but they look like the bug.
- **Repro to ask for:** an `.ntp` file plus a screenshot, and answers to these:
  - Does the edge appear after saving and reloading, or after moving either node? If yes, the cause is (b) or (c).
  - Is the destination a Merge or a Group, or did its input count change? If yes, the cause is (a).
  - Was the node pasted or created inside a group?
  - Is "Hide inputs" on in the node's Node tab?

**Render path today:**
- Both the Render menu entry (`Gui/Gui40.cpp:827`) and the Write node's Render button (`Engine/Node.cpp:6055`) send `firstFrame = INT_MIN` / `lastFrame = INT_MAX`. `AppInstancePrivate::validateRenderOptions` (`Engine/AppInstance.cpp:1897`) then resolves that to the writer's range, falling back to the project range, without asking.
- In the GUI, "background" today means non-blocking with the Progress panel. Setting `doBlockingRender = true` would call `blockingMap` on the GUI thread and freeze the UI, so "foreground" needs a modal progress dialog.
