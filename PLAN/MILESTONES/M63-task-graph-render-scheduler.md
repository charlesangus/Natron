# Milestone 63: Task-graph render scheduler

> **Elaborated 2026-10-04** (planning consultant, fable; clean run per the user's direction recorded under `## Decisions`). Architecture: a task graph built from the request pass, executed on the one global pool, with `renderRoI` as the task body. Decision draft: `DECISIONS/2026-10-04-task-graph-render-scheduler.md` (published at P6.T1).

Replaces the recursive pull-per-node execution of a frame with a scheduled task graph while keeping `renderRoI` as the unit of work. The request pass that already enumerates every (node, time, view) a frame needs is extended to record edges; a per-frame `FrameRenderContext` carries the frame args, request map, abort info and a `FrameStore` of produced images; an app-wide `RenderScheduler` runs ready node tasks on the one global `QThreadPool`, shared with the OFX multithread suite and host frame threading, ordered depth-first within a frame and frame-major across frames so independent branches and consecutive frames overlap with bounded intermediates. Cache rules, trimap, render-safety locks, identity and transform handling are unchanged because they stay inside `renderRoI`. A `renderSchedulerMode` setting keeps the legacy path so every render suite is checked both ways for bit-identical pixels. Writers first, viewer last; deep subtrees, OpenGL, roto strokes and analysis renders stay pull-inside-a-task in v1. Targets are stated in scaling terms (occupancy ≥0.8·P of the pool, frame time ≤0.8× where the graph's parallelism allows); the 4-core host gives the first data points only.

  - approach: singleton on `AppManager`. `submit(FrameRenderContextPtr, FrameGraph)` returns a `FrameFuture` (mutex + `QWaitCondition`, never waited on from a pool thread). Memory admission: a task with no started predecessors in its branch waits in the queue while `bytesInFlight` exceeds `getRamMaximumPercent()`-derived budget; tasks continuing a started branch always run, so progress is guaranteed. ## Decisions
- 2026-10-04 — **First elaboration rejected by the user** (plan commit `364ae032c` holds it for reference; its decision draft is removed). It proposed making the existing pull concurrent instead of a task graph and re-based the targets to this 4-core host's ceiling. The user's direction: re-run the design consultant clean on the `fable` model without exposure to that run; the design must scale to workstations with dozens of threads and hundreds of GB of RAM as well as modest machines, and must handle graphs with both large depth and large breadth; keep the task-graph architecture unless a clearly superior architecture emerges that meets those requirements.
- 2026-10-04 — **Elaborated (clean run, fable).** Task graph kept; see the decision draft. Twenty tasks in six phases; writers first, viewer last; legacy path retained behind `renderSchedulerMode`.
- 2026-10-04 — **P1.T1 landed (harness)**: `aabede08a`. `BENCH_SETTINGS` (semicolon `name=value` list → `--setting`), `range_parallelism`, `profile_run.sh SAMPLER=states`, `compare.py` keys on `settings`. **The baseline numbers are invalid:** the host carried an external load average of 12–19 during both runs (nothing of ours visible in `ps`; the sandbox shares the machine), every row came out 1.3–2.0x slower than After M62 with the same code, and occupancy means were 2.14–2.16 on comp/wide 100. The section stays in `BASELINE.md` with that caveat; P4.T2 re-takes the start baseline back-to-back with the after-run on a quiet machine. Rule from now on: check `/proc/loadavg` before any bench and record it in the section.
- 2026-10-04 — **B2 landed** (`cf5775f44` P1.T2, `f1bc4686a` P1.T3, `99d972cac` P2.T1). Debug build clean; FrameGraphBuild, RenderBothWays, RenderSchedulerMode and GraphScaling suites 23/23; full ctest 914/914. Notes: `--setting renderSchedulerMode=1` already works through `ChoiceParam::setValue(int)`; `OutputEffectInstance::reportStats` gained a `RenderStatsPtr` parameter so the counters reach the stats file. `FrameRequestMap` became a class (derives from the old map typedef) to carry the DFS counter. Request-mode `treeRecurseFunctor` now walks every frame but records edges only up to the prefetch cap, and recurses at the upstream mipmap level the render really uses (a behaviour change that only matters at mipmap > 0 with scale-one inputs). The edge-vs-call test compares key sets, not counts, because `getImage` re-enters `renderRoI` for pre-rendered frames. Known places where edges and calls could still disagree, none covered by the test: pass-through layer pulls, multi-rect renders, null-RoI consumers with request data, and a cache hit on a non-frame-varying node pulled at several times.
- 2026-10-04 — **B3 landed as one commit** (`7d55bd7e3`, P2.T2 + P2.T4): the two tasks interleaved edits in `ParallelRenderArgs.cpp` and `EffectInstance.h/.cpp`, so splitting by hunk was not reliable. Targeted suites 21/21 after a fix round; full ctest 917/917. Notes: `FrameStore::find` compares channel lists as well as layer IDs because `ImageLayerDesc::operator<` orders by ID only (an RGBA entry would otherwise satisfy an alpha request). `FrameContextScope` cleans up TLS only when it is the outermost scope; tasks must run on pool threads, never inline on a thread holding setter data; a plugin kernel thread spawned from a task sees only effects the task thread has touched. The request pass is now a work-stack driver (`visitRequestPassItem`), `treeRecurseFunctor` is render-only, and `collectPreRenderFrames` is shared by both passes. The deep-chain test (2000 OFX Grades: 63.5 s to build, 0.65 s request pass, on a 2 MB stack where the old recursion needed ~4.4 MB) had to pre-warm RoDs bottom-up: the cold RoD query recurses through the OFX host at ~2.2 kB per node, a depth limit independent of the pass. **New task P2.T5** addresses it; the legacy pull shares the limit.
- 2026-10-04 — **B4 implemented, building** (P2.T3 store-aware hand-off; P3.T1 `RenderScheduler`). Implementer notes to carry into later tasks: the installed frame context is per thread and is not passed to threads spawned for host frame threading, so a tiled worker's `getImage` falls back to the pull and counts an unplanned pull (P3.T3 must propagate the context through `SpawnedThreadScope`); a downscaled image produced by a node without render-scale support is created without `setKey()` (`EffectInstanceRenderRoI.cpp:~1351`), so the seeded-conversion path misses it and re-renders (correct, slower); `getImage` skips the input's `renderRoI` outright on a direct store hit; the pass-through-layers path (`EffectInstanceRenderRoI.cpp:~489`) also consults the store because a disabled node pulls its input there, not through the identity path. Scheduler: store consumer counts come from graph edges (per mipmap), not `FrameViewRequest::consumers`; inputs are released before the output is put; memory admission has a fallback (admit when running tasks' estimated output plus in-flight bytes fit, or when nothing runs) because holding back every leaf-fed merge would deadlock; `callerRenderTime` is the first consumer's time as in the pull.
