# openfx-gmic is deferred: its pinned source no longer exists

The decision to build the full upstream OFX plugin set (M13) covers
openfx-arena, which is proven, and defers openfx-gmic, which is not blocked on
dependencies.

openfx-gmic's dependency list is small — it never runs G'MIC's own build system,
compiling `gmic.cpp` as a single translation unit with its own flags. Only
`fftw3` is missing from `aswf/ci-vfxall:2027-clang21.1`, and that is reachable
and cheap to build. `-Dcimg_display=0` means no X11 is needed.

**The blocker is source availability.** `GMIC_OFX/Makefile` hard-pins
`GMICVER=2.8.4` and fetches `http://gmic.eu/files/source/gmic_2.8.4.tar.gz`.
Measured from inside the container on 2026-09-02:

- `gmic.eu` resolves, then gives `No route to host` — the same egress-allowlist
  signature as `dl.rockylinux.org` in
  `2026-08-30-sealed-package-network.md`.
- `GreycLab/gmic` on GitHub was created 2023-04-23, its oldest commit is "Clean
  repository", and its 39 tags start at `v.3.2.4`. The tag `v.2.8.4` returns
  404. G'MIC 2.8.4 is simply not on GitHub.
- `dtschump/gmic` is 404. Software Heritage and SourceForge's mirror CDN are
  both unreachable.
- The project's other three fetches, from `GreycLab/gmic-community`, *are*
  reachable — so only the tarball is missing.

Bumping the version is not a workaround. Upstream's own Makefile carries
`#GMICVER=2.9.0 # config file changed & broke plugin (shows 0 plugins)`, issue
\#3 "Update G'MIC to 2.9.x" is still open, and the repository has been dormant
since February 2024. `Helpers/gmic_parser.cpp` synthesises the OFX plugin list
by parsing `#@gui` blocks out of the G'MIC standard library; current G'MIC is
4.0.5, two stdlib format generations ahead. A port is multi-day work with a
documented failure mode of producing zero plugins.

Two other facts worth recording. openfx-gmic's `CMakeLists.txt` must not be
used — its source glob omits `gmic_plugin.cpp`, `gmic_parser.cpp` and
`gmic_libc.cpp`, every OFX entry point — so the Makefile path is the only one
that works. And `gmic.cpp` plus `CImg.h` is roughly 78,000 lines in one
translation unit, which `-j` cannot parallelise: upstream's own build script
singles it out as needing `--param ggc-min-expand=20 --param
ggc-min-heapsize=32768`, and it would add 10-30 minutes and 3-4 GB RSS to a CI
step that Phase 13.1-13.2 already grows to ~16 minutes.

**What would unblock it**, in ascending cost: mirror `gmic_2.8.4.tar.gz` into a
repository we control and fetch it from `raw.githubusercontent.com` with
checksum verification (which would also restore arena's `ReadSVG` and
`ReadCDR`, whose librevenge and libcroco sources are likewise unreachable);
widen the egress allowlist to `gmic.eu`, revisiting the sealed-network decision
that already flags this as worth reconsidering; or port openfx-gmic forward to
G'MIC 4.x.

Because gmic will not ship, the 360 `eu.gmic.*` pages under
`Documentation/source/plugins/` — half the plugin reference — are removed in
M13.P4.T2 rather than left claiming capability the tree does not have. They are
generated by `tools/genStaticDocs.sh` and regenerate if gmic is ever built.
